# L-110：查重闸门只查「对外」不查「对内」，等于在最需要它的时候瞎

第 111 轮。起因是我要补语义查重闸门时自己造出来的第二个盲区。

## 事故经过

上一轮我派了 8 个出题子代理同时出 A10 到 A17，每份任务书只给「出题前」的标题清单让它们避撞。
结果 A11-01「空调设成二十六度」与 A16-02「空调要开多少度」同时产出——
**字面不同，是同一考点**。这正是用户点出来的：「你要保证题目不重呀」。

我先后试了三种字面口径，**全部漏检**：

| 口径 | 查什么 | 为什么查不出 |
|---|---|---|
| 标题归一化 | 去掉停用词后的实词集 | 标题本来就不一样 |
| 词袋签名 | 全文去停用词后的词集 | 同构是「同考点 + 换人物换数字」，词集必然不同 |
| 问句主干 | 题干去疑问词后的实词集 | 问法不同（set / turn on） |

**三次都失败，说明「换个更聪明的字面规则」这条路本身是走不通的**——
语义重复不是字面问题，靠字面规则永远抓不全。必须换表征。

换成 EmbeddingGemma 300M 后一次抓到（0.783）。

## 但闸门本身又有个盲区，是 reviewer-1 指出来的

我写完 `check` 只测了 `build` 与 `scan`，没测 `check`，也没想清楚
「候选题彼此之间要不要比」。于是：

- `check` 只把候选题与**索引**比
- 索引靠 `build` 增量更新，谁先 build 谁先进
- 出题员是**并行**写多批的，后写的批次如果没赶上 build，就查不到前一批

**结果就是：我给每个出题员都写了「写完必须 build」，用流程纪律去补工具的缺陷。**
而流程纪律恰恰是最容易在赶进度时被跳过的一环。

**修法**：check 额外做候选题两两比对，超阈值单独列出「候选题彼此重复」小节，
退出码同样为 1。**这不依赖任何 build 顺序。**
实测：拿两条改写版空调题测试，批内相似度 0.976 被抓出。

## 推广

**凡是一个闸门只检查「输入 vs 既有状态」，就要问一句：它检查「本次输入内部」吗？**

批量作业里，输入内部的两两冲突是最常见的一类缺陷，而只做「对外比对」的闸门
**恰好在最需要它的场景（并发、批量）里失效**——因为并发的定义就是「本次输入之间会互相影响」。

这个盲区和 PIPELINE L-109 是同一类错误的两个方向：

- **L-109**：「取最新的那个」把实现细节当成流程顺序 → **顺序定义错了**
- **L-110**：闸门只对外不比对内 → **比对范围漏了一半**

两者共同的教训：**你以为检查覆盖了，实际上只覆盖了一部分，而漏掉的那部分恰好是最容易出事的。**

## 顺带记两条

1. **闸门上线前必须自测三个子命令全跑一遍**，不能只测最常用的那个。
   我建完闸门就拿去派活，`check` 是出题员唯一真正会用的命令，而我根本没跑过它。
2. **「我给每个执行者都写了纪律」是一个危险信号**——它通常意味着工具没做到位，
   而在赶进度时纪律是最先被牺牲的。**能用工具保证的，不要交给纪律。**
