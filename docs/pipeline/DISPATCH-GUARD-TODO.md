## 缺陷一｜`record_post_md5s` 第 157 行的退回路径会造出假证据

```python
return post if post else head      # L157
```

`head`（第 153 行）收集**所有不以「## 中文数字」开头的行**上的 MD5，**不区分修前修后**。

### 实测链（不是推理，是跑出来的）

```
$ python scripts/dispatch-guard.py touched A24
  当前磁盘：3b52e5bc62484e99b6eaa0045569506f
  R1 记录的 MD5：4bf93404e74f7bbf532deb6d629cca5e
  - data/item-bank/fixes/F2-A18toA28-REBUILT.md（磁盘 MD5 在记录「修后」集合内）
```

该记录第 29 行：
```
| A24.md | 4bf93404… | 3b52e5bc… |
```

**关键点：L29 这一行本身没有「修后」二字——「修前/修后」写在表格的表头行里。** 于是：

| 步骤 | 判断 | 结果 |
|---|---|---|
| L151 | L29 含「修后」吗 | **否** → 不进 `post` |
| L153 | L29 是「## 中文数字」开头吗 | **否** → 整行进 `head`，**修前的 4bf93404 和修后的 3b52e5bc 一起进** |
| L157 | `post` 为空 | 退回 `head` → 命中 |

### 结论

**现在这个匹配是「对的」，但是靠退回路径蒙对的，不是靠修后逻辑判对的。**

**一旦 A24 被回滚成 `4bf93404`，`head` 里同样有它 → 照样报「在修后集合内」→ 凭空匹配 →
在 `agent` 档会造出阻断派工的假 CONFLICT。**

### 修法

1. **只含「修前」而不含「修后」的行，其 MD5 必须排除。**
2. **配对行（同时含修前与修后，或表格内修前列与修后列）取最后一个 MD5 作为修后值。**
3. 一行只有修后值时取该行全部。
4. **取不到任何修后值时，不要退回「全部 MD5」，返回空集让调用方判 UNKNOWN。**

> **第 4 条最要紧。** 「宁可 UNKNOWN，不要假阳性」是这个脚本的设计约束（第 3 条）。
> **退回全集会与它自己的设计约束直接冲突。**

## 缺陷二｜`agent` 以署名为判据

```python
verdict = UNKNOWN if author is None else (CONFLICT if author == args.name else OK)   # L186
```

`record_author`（L127）取「执行者：」行。**但署名是本轮事故后才补的约定，90 多份既有记录都没有署名**
→ 全部落进 `UNKNOWN` → L218 `return 1` **阻断派工**。

### 改三档

| 档 | 条件 | 含义 |
|---|---|---|
| `CONFLICT` | 声明改了某批 **且** 磁盘 MD5 == 其修后 MD5 | 强证据，该执行者确实动过这批 |
| `WEAK-MATCH` | 只有声明，无 MD5 可核 | 提示，**不据此阻断派工** |
| `UNATTRIBUTED` | 磁盘 MD5 与 R1 基线不同，但无任何记录声明 | 改动存在、无人署名 |
| `OK` | 声明改了别的批 | 无交集 |

**署名从 L190 的输出行降级为独立统计**（「全库 N 份记录无署名」），**不参与判定**。

## 验收夹具的坑

`record_declares`（L110）要求记录里有 DECL_KEYS（L41：被修文件／被改文件／修复文件／修改文件／被修批次）之一。

**只写「修前 X / 修后 Y」会被整条忽略**，于是得到一个**「看起来没报错、其实是因为记录被忽略」的假通过**。

**所以验收夹具必须额外带一行**：
```
| 被修文件 | data/item-bank/prod/A24.md |
```

> **推广：「没报错」不等于「检查通过」。**
> **一个查询没返回结果，可能是「检查通过」，也可能是「根本没被检查」——这两者必须分开确认。**
