## 四、继续推进的方法

每个批次的流水线是固定的五步，**顺序不可跳**：

```
R1 独立审核 → F1 修复严重+中等 → R2 独立审核 → F2 修复 → V 修复后复核 → 归档
```

### 派单纪律（血的教训）

1. **报告与 fixLog 的文件名必须机械推导**，严禁手写编号。review 叫 `R2-Xxx.md` 则 fixLog 必须叫 `F2-Xxx.md`。已因手写编号差点让子代理覆盖他人记录。
2. **二轮审核员必须禁止读** `reviews/` 其他报告、`fixes/` 任何文件、`docs/pipeline/`。`docs/pipeline/` 含前几轮结论转述，会污染独立判断。
3. **修复员必须禁止读** `reviews/` 其他报告与 `fixes/` 其他文件。
4. 所有审核与修复任务**开头都要做字节校验并记录 md5**。本项目出现过读取工具返回文本与磁盘在三处不一致，若沿用会得出错误结论并凭空多出材料里没有的信息。

### 归档门禁（INDEX.md 逐项机器判定）

周期 0 ｜ 最长连续相同 ≤2 ｜ 相邻同说话人 0 ｜ Excuse me 起句 ≤30% ｜ 一轮二轮复核报告齐备。

### 已知会漏、需人工盯的四类

1. **结构比**（每份材料配几题）——逐题质量检查覆盖不了，已导致 B2 整批错标类别。
2. **新增题未被审核**——补写的题要当新题逐题审。
3. **共享约束**——改表格填空的词库行序或任何一篇的答案字母后，必须**全卷重跑**字母覆盖、逐空偏斜、周期检测。
4. **标注与问句的一致性**（E 类）——考点示例的方向、人称切换、情景是否预设答案，都需逐个分支代入验证。

## 五、本项目沉淀的方法论

`PIPELINE.md` 记录了 41 条教训，其中最值得保留的几条：

- **L-09 / L-10：修复环节是严重缺陷的主要来源。** 二轮发现的 9 条严重缺陷，绝大多数由修复引入，原始产出贡献极少。任何「按审核意见做局部文本替换」都可能造出新缺陷。
- **L-28：「换了位置的假修复」。** 改完后要问「原先导致缺陷的那个要素，现在还在吗？」
- **L-32 / L-39：约束必须有可复现的度量方式，否则它不存在。** 结构比、周期检测、词数口径都先后栽在这上面。
- **L-23 / L-34：审核员给出的替换文本本身会错（累计 12 例）。** 修复员必须把建议当草稿。**这 12 例全部由修复员拦下，无一漏进题库**——这是整条流水线唯一从未失效的防线。
- **L-31：两端都用可证伪的方式自证。** 审核端用双路径字节比对证明「我读到的是真的」，修复端用逆向补丁 md5 证明「我只改了该改的」。
