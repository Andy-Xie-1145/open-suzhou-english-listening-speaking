# L-111：闸门悄悄忽略了自己的输入，然后报出一个看起来正常的结论

第 113 轮补记（第 111 轮建闸门，第 112–113 轮修闸门）。这一轮修了九个闸门 bug，
其中**三个是同一类错误**，而且是同一类里最难发现的那种。

## 一句话

**闸门最坏的失效模式不是报错，是「一直在跑、一直在报数字、但那个数字没有意义」。**
报错会被人看见；一个看起来合理的数字不会。

## 事故经过：三个同类的 bug

### 1. `encoding-check.ps1`：把「末尾无换行」过滤掉，再判 PASS

原实现把「末尾无换行」从失败集里筛进另一个集合，然后拿剩下的判 PASS。
**于是这一项永远不可能 FAIL。**

讽刺的是：**这个闸门正是为「查 C3.md 末尾少一个 LF」而建的**（见脚本第 5 行自述）。
**建它的原因和它的行为正好相反。**
更糟的是第二层伤害：同时存在末尾缺 LF 与其他真缺陷的文件，会因为这一条过滤而**整条从失败集消失**——
一个本来能被报出来的文件，变成了一个干净的文件。

### 2. `shortcut-audit.ps1`：把每道题的答案配上**下一题**的选项去比长度

原逻辑在遇到 `**Answer** X` 时才把手上累积的选项冲出去，于是
**Q1 的答案被配上了 Q2 的选项、Q2 的答案被配上了 Q3 的选项……**

「正确项总是最长／最短」这两条启发式**一直在拿下一题的选项去比**，测出来的是垃圾。
reviewer-2 独立测出 C 类真实偏差 **50–73%（其中一处 66.7%）**，而这个闸门一直报 **7.3%**。

**7.3% 这个数字不但没用，而且比报「可疑」更坏**——它让所有人相信 C 类没问题。

### 3. `speaker-gate.ps1`：没有 `param()` 块，文件路径参数被静默丢弃

`-File script.ps1 某个文件.md` 把参数放进 `$args`，而脚本全文 151 行**从不读 `$args`**，
第 54 行起直接全库扫描。**路径参数被丢弃，没有任何报错。**

后果是验收标准本身失效：任务书写「改完必须闸门对该文件退出码 0」，
但**即使目标文件修得完全干净，只要库里别的文件还有缺陷，退出码就恒为 1**——
这条标准**永远无法判定**。
我实测连跑 A18 到 A28 共 11 次，**每次输出完全相同（都是 32 条）**，才确认参数没生效。

## 为什么三条都没人怀疑

| 共同点 | 说明 |
|---|---|
| **输入被丢弃或错配，但没有报错** | 脚本正常执行、正常退出、退出码有值 |
| **输出的数字看起来合理** | 7.3%、PASS、退出码 1——全都在「正常范围」里 |
| **正因为合理，才没人怀疑** | 一个荒谬的数字会引人去查；一个合理的数字只会被人引用 |

补一句更要命的：**这三条都不是逻辑写错。**
每一段的代码单独看都成立：过滤、累积、按批次循环——它们只是**各自多做了一件事或少做了一件事**，
而那件事没有任何一处会报错。**「看起来在工作」正是它们能活到被发现的原因。**

## 另三条不同类的 bug（同样值得记）

4. **`topic-guard build` 按 `key = 文件名::题号` 跳过，完全不看内容。**
   后果：**修复员改完题目再跑 build，改动进不了索引**，语义闸门对改过的题继续用旧向量。
   更隐蔽的是：**索引里明明存着旧文本，`build` 却报「已是最新」**——又一个看起来正常的结论。
   修法是给每条索引项记文本哈希，内容变了才重编码。
   （首次运行旧索引没有哈希字段，于是 579 条全被判为「变了」而整体重算——一次性成本，之后收敛。）

5. **`shortcut-audit` 的 D 类解析两处错位**：
   词库建在**文件级**而不是 `##` 标题级，一份文件里 10 份材料的词库被合并成同一个字典；
   槽位又只从 `**Answers**` 的下一行取，而文件末尾的「本批汇总」行把全批答案**又写了一遍**。
   两者叠加，D 类槽位数虚高——单份 D6 被读成 60 空（实为 30），全库一度报 **150 而实际 120**。
   修法之外还加了一道**解析器自检**：“D 类槽位数 = D 类材料数 × 每份空数” 是硬等式，不等即先修脚本、**再谈启发式结论**。

6. **逐题极差检查报出问题却不给题号。**
   它能算出「某批次某处多 N 词」，但说不出**是哪一题**。
   **报出问题却不给位置，等于把活推回给人工去反查**——调度方拿不到可派的单。
   修法是把 `Id` 一路带进输出（如 `A28-13-Q2`）。

## 推广：闸门上线前的检查清单

以下每一条都对应上面至少一个真实事故，不是预防性套话。

### 一、上线前把**每个子命令**都跑一遍

**不能只测最常用的那个。** topic-guard 是我的反面教材：我建完就直接拿去派活，
而 `check` 是出题员唯一真正会用的命令，**我从头到尾没跑过它**——
于是它「只对外不对内」的盲区，直到 reviewer-1 指出才发现（见 L-110）。

判定标准：**数一遍脚本有几个入口，逐个跑过，并为每个入口留一份「已知输入 → 已知输出」的记录。**
没有这份记录的入口，等于没测过。

### 二、闸门里的**范围与阈值**，问一句：**它是推导出来的，还是惯例？**

这条不是新教训，是 **L-85** 的第三次复发：
「范围与阈值若是惯例而非推导，就会在数据变化后静默失效」。

- 阈值 0.75 是对 419 份材料标定出来的 → 数据涨到 694 条后它还成立吗？**要重新标定并留下日期。**
- 「SPEAKER-COUNT 只适用于 A 类」是推出来的（B/C 允许多人，D 类专项要求 ≥4）→ **不要照抄到新类别上。**
- 「单类阈值 35% = 随机基线 25% + 10 个点」是**惯例**——它没有随「命中率该怎么随类别变化」重新推导。

**凡是一个数字，写下它时必须同时写下「它是怎么来的」。写不出来就是惯例，惯例要标注。**

### 三、闸门报 PASS 之前，**先造一个已知有病态的输入喂给它**

这是本轮三条同类 bug 唯一有效的抓法。**没有病态输入的自测，等于没自测。**

本轮实际用过的病态输入：

| 闸门 | 病态输入 | 期望 | 若没抓到说明 |
|---|---|---|---|
| `encoding-check` | 一个末尾无 LF 的 md | FAIL | 这一项被判成了「不可能 FAIL」 |
| `shortcut-audit` | 一份 Q1/Q2 选项长度刻意不同的批 | 两条启发式都命中 | 答案与选项错位一题 |
| `speaker-gate` | 传一个具体文件路径 | 只扫该文件 | 参数被丢弃 |
| `topic-guard build` | 改一句题面后重跑 build | 重编码 | 内容变化进不了索引 |
| 逐题极差 | 一题正确项比干扰项长 10 词 | 报出且**带题号** | 只报聚合率，或不给位置 |

**「报不出」和「报得出但没有位置」，是两种不同的病，前者更隐蔽。**

### 四、**「永不 FAIL」的检查项比没有检查项更危险**

因为它提供**虚假的安全感**：报告上写着「文件可用性闸门：PASS」，读的人会认为文件可用性已被验证。
实际上那一项从来没生效过。

判定方法很直接：**看每一项检查在最近 N 次运行里 FAIL 过几次。**
**长期一次都没 FAIL 的项，要么是库真的干净，要么是这一项坏了——必须人工确认是哪一种。**
同理，一个**长期只报同一个数字**的检查项，也值得停下来问一句「这个数字今天还成立吗」。

### 五、**聚合率与逐题检查互补，不可互相替代**

本轮最反直觉的一条。A 类「正确项总是最长」聚合率 **15.9%**、阈值 35%、判「正常」——
而 **A28-13 的正确项比最长干扰项多 7 词**，单题就能被套捷径，**被聚合率稀释掉了，闸门根本没报**。

- **聚合率抓「系统性倾向」**：整批的倾向会让「一律选最长」可套。
- **逐题极差抓「极端个例」**：单题就能被套，与整批倾向无关。

**「聚合率过了」不等于「每一题都过」。** 这是实测反例，不是推演。
（对称地，混算会把**某一类的系统性缺陷**洗成正常——这正是 C 类 66.7% 被报成 7.3% 的另一半原因。）

### 六、**闸门报出问题必须带位置**

没有题号的缺陷清单不可派单。**「某批次某处」等于没报。**
凡是输出缺陷列表的闸门，每一条都要带**批次 + 题号 + 判据数值**三样，缺一不可。

### 七、**脚本的注释要写「为什么这样写」，并把 bug 史留在注释里**

本轮三个脚本的注释里都留下了「第 N 轮修 X bug，原实现是 Y，症状是 Z」。
这不是冗余——**下一个人删掉这段注释，就可能把 bug 改回去**，因为原实现看起来是合理的。
LESSON-110 那次事故里，我重写 check 的读法时差点又把「候选题彼此比对」删掉。

## 最后一句

**L-109、L-110、L-111 是同一个错误的三种说法：**
**你以为检查覆盖了，实际上只覆盖了一部分；而漏掉的那部分，恰好是最容易出事的。**

前两次漏掉的是**范围**（该比的不比、该取最新的没取最新），
这一次漏掉的是**输入本身**（输入进来了、被丢弃了、错配了，闸门却照常报数字）。

**它们的共同点不是「粗心」，而是「闸门表现得像在工作」。**
所以对策也不是「更仔细一点」，而是**逼闸门证明它真的在工作**——
用病态输入逼它、用等式自检逼它、用「这一项最近 FAIL 过一次吗」逼它。
