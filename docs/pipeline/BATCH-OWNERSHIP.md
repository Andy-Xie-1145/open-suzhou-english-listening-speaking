## 硬规则

1. **一张批次表只能有一个 owner。** 派工前先查本表，不得凭记忆。
2. **审核员不得自行扩大范围。** 手上批次做完后，**先回报调度方领下一批**，不得接着做「下一批看起来也没人做」。
   ——A30 的撞车就是这样发生的：reviewer-1 报完「A31、A32 接着来」，而 task-17 已把这两批派给 reviewer-2。
   > **⚠️ 本条只堵住这一种越界，不解决重叠派工。**（第 113 轮更正）
   > reviewer-2 指出：他遇到的三次撞车**全部是调度方派了重叠范围**，他一次也没自行接批。
   > **真正堵住重叠派工的是上面那张归属表——派工前查表，不凭记忆。**
   > 调度方的表述「四次撞车都是派工失误」对 reviewer-1 那次成立，对 reviewer-2 三次不成立。
3. **落盘前必查同名文件是否已存在。** 已存在则**不覆盖**，改写为 `R1-<批次>-2.md` 并在报告首部写明理由。
4. **同批次多份报告以文件名后缀最大的那份为准。** 两份都保留，不删。

## ⚠️ 查板面前必须显式传 `limit: 100`（第 113 轮，调度方与 writer-bcd 各栽一次）

**`team_task_list()` 默认只返回前 50 条。**

```
team_task_list()                 -> 50 条   ← 默认，截断
team_task_list({limit: 100})     -> 63 条   ← 真实值
```

**「最多 50 条」「最大编号 task-50」正是默认值的截断边界，不是真实上限。**
读错会得出「任务不存在」「板子满了」「板上只剩一条在跑」这类结论——
**本轮调度方据此判断过好几次未完成任务数，那些数字全是截断后的。**

**这是本轮「闸门/视图只告诉你被检查的那一面」的又一例**，与以下同形：
- `encoding-check` 不扫 `fixes/`（五份记录被清空时它全绿）
- `shortcut-audit` 的 35% 阈值按类设（500 题），不是按批设（15 题）
- `topic-guard build` 报「索引已是最新」——那次是改动前跑的
- 反向替换闭合证明只覆盖**已申报**的改动

**共同形状：一个查询接口给了你一个看起来完整、实际被某一维截断的结果。**
**处置：凡是「查全库 / 查全板 / 查全部」的调用，先确认它有没有返回上限提示，并主动放大 limit。**

## 文件名里的范围标签 ≠ 被改文件清单（第 113 轮补）

**派单前必须核修复记录的结论节列的是哪些文件，不能从文件名推。**

**实例**：调度方据 `fixes/F2-A18toA28.md` 的**文件名**写下「A18/A22 换过题」，派了 R2 去审修复。
**该记录的结论节写的被修文件是 `A24.md`、`A26.md`、`A28.md`——A18 只出现在文件名里。**
A18 / A22 / A23 三批**自 R1 起零字节改动**，任务前提整个是错的。
**由 reviewer-2 查出**（按批名限定路径检索 `fixes/` 全目录，确认无任何记录声明过这三批的改动）。

**同类命名**：`B6toB7`、`A29toA30`、`A14toA17`、`F1-A32` 等一律是**区间或批次代号**，不是改动清单。
**F1-A32 的确只改了 A32，是例外不是通例——不能从一个推另一个。**

**判据**：**「某文件出现在修复记录的文件名里」不等于「该文件被修改过」。**
**零改动时的闭合证明比有改动时更强**——文件与 R1 基线逐位相同，不需要替换即闭合，任何人重算一次 MD5 就能复现。

## 顺序约束：V 轮必须排在它所验证的那轮修复之后（第 113 轮补）

**这不是风格建议，是硬约束。** 本轮已四次撞上同一件事：**把基线指向一个会被后续改动的东西**。

| # | 现象 | 后果 |
|---|---|---|
| 1 | 0.813 那对无人裁决 | 缺陷长期挂盘，闸门持续 FAIL |
| 2 | C7/C8/C9 的 V 报告锚的是 F2 加词**之前**的 MD5 | 时间戳可证：C7.md 落盘 09:13:50 晚于两份 V 报告 09:06 / 09:07 |
| 3 | task-47（D7-01 + C9 前三篇）落盘 | V-D7、V-C9-3 两个锚同时失效 |
| 4 | task-45（A12-11/A16-04）落盘 | V-A16 失效 |

**规则**：
1. **V-<批次> 的 blockedBy 必须是该批次最后一轮修复任务。** 修复未完成前不派 V。
2. **修复一旦又动了已锚定的文件，必须补 `-<下一个可用后缀>` 重锚**，并在报告里写明「结论沿用哪一份、只重算基线」。
3. **V 轮的结论范围必须与实际核验范围一致**：分批交付时说清覆盖哪几篇，不许用「本批通过」覆盖全库。
4. **落点取「下一个可用后缀」，不是一律 `-2`**（见 _COMMON.md 同名条款）。

**根因**：这四条约束此前只存在于调度方的判断里，**没有落在可执行的地方**——规则不落到板上就会被忽略。
**判据**：凡「V 报告的基线所指向的文件，在报告写完时还有已知的未完成修复」，就是违反本条。
