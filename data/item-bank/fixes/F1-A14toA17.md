## 9. 工具问题：topic-guard.py build 不重编码已编辑条目（该声明不成立，给出反证）

task-7 硬要求第 4 条写「改完跑 `python scripts/topic-guard.py build` 把改动并进索引」。**我照跑了，但这一条声明不成立。**

**实测输出**：
```
索引已是最新：579 条，无新增
BUILD_EXIT=0
```

**根因**（scripts/topic-guard.py 的 cmd_build 函数）：
```
known = {it["key"] for it in idx["items"]}
...
    key = f"{m['file']}::{m['id']}"
    if key in known or key in seen:
        continue
```

增量判据**只看「文件名::题号」这个 key，不看内容**。A14-14、A15-03、A15-04、A16-02、A17-10、A17-12 的 key 早已在索引里，于是全部被跳过——**向量仍是旧文本的**。

**实测后果**：紧接着跑 `python scripts/topic-guard.py scan`，仍然报出旧标题：
```
索引 579 条｜阈值 0.75｜跨批次疑似重复 35 对
      A14-14     A14.md         煮鸡蛋十分钟
      A15-03     A15.md         地震演练躲到桌下
      A15-04     A15.md         声控灯坏了找物业报修
      A16-02     A16.md         空调要开多少度
      A17-10     A17.md         停水要停几个小时
      A17-12     A17.md         上个月电费多少钱
```
**这是索引陈旧造成的假重复，文件本身已改对**（§8 已用关键字扫描证明）。

**对本轮闸门结果的影响：无，反而更严。** §3 的 check 是拿**新文本**去比对**含旧版本的索引**——即 A14-14 的新题要和索引里的「煮鸡蛋 A14-14」「煮鸡蛋 A17-06」都比一遍。退出码 0 因此是一个**比清空索引后重测更强的结论**，不影响有效性。

**我没有自行删除重建索引，理由**：
1. .topic-index.json 是**多代理并发共用的共享文件**，删除会让同期其他出题员的 check 在几分钟内**静默放行一切**（fail-open），比索引陈旧更危险；
2. 重建 579 条向量耗时数分钟，期间同样 fail-open；
3. 任务书写明「不许碰脚本规约」，我不改脚本，也不擅自销毁共享数据。

**建议调度方二选一**：
- (a) 在**无并发**的时点删掉 data/item-bank/.topic-index.json 再跑一次 build 全量重建；
- (b) 修 cmd_build：把增量判据从 key 改成 key ＋ 正文哈希（key 后面拼一个正文 sha1 的前 12 位），再在载入索引时按前缀剔除同名旧条目。这一处改动能根治「改了题却查到自己旧版本」的问题。
